# OpsPilot 开发提示词包

> **用途**：把任务派给 AI 时直接复制对应提示词。每段都可以独立使用。
> **配套**：`交接文档.md`（人看）、`OpsPilot-需求开发文档.md`（真相源）、`前端实现规格与开发提示词.md`（前端）

---

## 使用说明（先读）

1. **提示词不替代文档。** 每段提示词开头都列了「需附件」，附件必须真的给到，否则 AI 会自己编。
2. **每次新会话都先贴「提示词 0」。** 它建立红线，后面的提示词都建立在它之上。
3. **一次只派一个任务。** 不要把 M1 和 M3 塞进同一段提示词。
4. **AI 交付后，用「提示词 6」做红线审查**，再合并。
5. 需要改规格时：让 AI 起草修订条目，由 mir Y 确认后写进需求开发文档的 §D —— **不要让 AI 直接改规格**。

**附件速查**

| 提示词 | 必须附带的文件 |
|---|---|
| 0 通用开场白 | `docs/OpsPilot-需求开发文档.md` |
| 1 源码索引 | `upstream/`（两个仓库目录） |
| 2 get_server_health | 需求文档 + `upstream/software-agent-sdk/` |
| 3 后端底座 | 需求文档（重点 §A6.5 / §A9 / §A10） |
| 4 风险与审批 | 需求文档（重点 §A5.2 / §A6.2 / §A6.5） |
| 5 前端 | `前端实现规格与开发提示词.md` + `assets/` + `prototype/` + 需求文档 |
| 6 红线审查 | 需求文档 + 被审查的代码 |

## 提示词 0 · 通用开场白（每次新会话必贴）

```text
你将参与「OpsPilot」项目的开发。在动手之前，请先读完下面的规则，然后用你自己的话复述一遍红线，
确认你理解了再开始。如果任何一点不清楚，先问我，不要猜。

【项目一句话】
OpsPilot 是一个以 AI 聊天为核心的通用工程 Agent 工作台，基于 OpenHands（MIT）二次开发：
保留其代码生成、文件操作、终端执行、Git、测试运行等通用工程能力，在此基础上叠加
SSH、数据库、Docker、Kubernetes、日志与监控的运维能力。
它不是"只能做运维的 Agent"，也不是 SSH 客户端或监控大屏。

【唯一真相源】
《OpsPilot-需求开发文档.md》（本次已附上）是唯一真相源。
- 不得新增、删除、改名任何工具名 / 状态名 / 风险等级 / 字段名 / API 路径
- assets/ 目录下的效果图是界面示意，其中所有主机名、IP、百分比、耗时、日志内容
  均为演示占位，与规格冲突时以规格为准
- prototype/ 目录下的 HTML 是原型稿，不是规格

【十条红线】
1. 工具名只能来自规格 §A5.2 的命名表，禁止自造（例如不要出现 exec_readonly_cmd、
   get_system_metrics 这类名字）。
2. 任务状态只能是规格 §A7 的 16 个枚举值：RECEIVED / CLASSIFY_TASK / SELECT_CONTEXT /
   PLAN / INSPECT / ANALYZE / PROPOSE_FIX / WAITING_APPROVAL / EXECUTE / VERIFY /
   REPORT / COMPLETED / FAILED / CANCELLED / TIMEOUT / WAITING_USER。
   禁止另起小写别名。
3. 风险等级只有 L0–L5（§A6.2），且 L5 在任何权限档位下都不得自动执行。
4. 权限档位只有三档：请求审批 / 帮我批准 / 完全访问（§A6.5）。
   升级到完全访问必须先经过升级确认面板；降级不需要确认。
5. 凭据（私钥 / 密码 / Token / 真实 IP）永不进入 prompt、Observation、日志。
   验收方式是打印完整 prompt 逐字搜索。
6. 异常判断写在工具的 Executor 内，不交给 LLM —— 输出才稳定、可测、换模型不掉链子。
7. 不要自建框架已有的东西：审批引擎（用 ConfirmationPolicy + SecurityAnalyzer）、
   凭据隔离（用 SecretRegistry）、Agent 循环（用 SDK）、事件流（用 REST+WebSocket）。
8. 上游版本已 pin 死：agent-server 1.46.0 / agent-canvas 1.18.0 / automation 1.11.1，
   且 agent-client-protocol 必须锁 <0.11。不得浮动升级。
9. 里程碑以"能演示"为验收标准，不以"写完了"为标准。
10. 任何任务的验收都需要可复现证据：截图 / curl 输出 / 单元测试 / 打印的 prompt。
    不接受"应该可以了"。

【技术底座现状】
OpenHands V1 = SDK 四包（openhands-sdk / openhands-tools / openhands-workspace /
openhands-agent-server）+ Agent Canvas 前端（React 19 + Vite + Tailwind + Zustand）
+ Automation Backend。三服务栈由 ingress 代理按路径路由。
框架已提供、禁止自建：Agent 循环、审批引擎、凭据隔离与脱敏（SecretRegistry）、
事件流、暂停恢复、上下文压缩（Condenser）、多模型路由（LiteLLM）。
需要自建：资源管理后端（FastAPI）、任务状态投影（16 态）、业务级审计表、前端三栏工作台。

【当前进度】
规格、效果图（15 张）、交互原型（13 个状态）、任务拆解（M0–M7）已完成。
一行项目代码都还没写，从 M0 开始。任务清单见《开发任务拆解.md》。

请先复述红线，然后等待我分配具体任务。
```

## 提示词 1 · M0-4 源码索引（开工第一件事）

```text
【附件】upstream/openhands/ 与 upstream/software-agent-sdk/ 两个目录。

【背景】
OpsPilot 基于 OpenHands 二次开发。官方文档、论文、第三方资料对内部结构的描述不完全一致，
所以我们要求：所有关于"框架怎么接"的假设，必须以本地实际代码为准。

【任务】
在 upstream/ 两个仓库里，把以下 5 个关键点的实际位置找出来，产出一份《源码索引》：

1. 工具注册点 —— 我们自定义的运维工具要注册到哪里？
   要找：ToolRegistry / register_tool 的定义与调用位置，以及一个现有工具
   （例如 execute_bash 或 grep）的完整注册链路（Action / Observation / Executor /
   ToolDefinition 四件套分别在哪个文件）。

2. 工具执行点 —— Action 是在哪里被转成 Observation 的？
   要找：Executor 的调用入口、超时处理位置、异常如何包装成 Observation。

3. 确认策略接入点 —— ConfirmationPolicy 与 SecurityAnalyzer 在哪里被调用？
   要找：readOnlyHint=False 触发的 LLM 风险预测代码位置、确认策略的配置入口、
   会话中动态修改策略的 API（如果有）。

4. 事件流字段 —— 前端通过 WebSocket 能收到哪些事件？
   要找：事件类型枚举（MessageEvent / ActionEvent / ObservationEvent /
   AgentErrorEvent / AgentStateChangedObservation 等）的定义文件，
   以及每种事件的关键字段名。这一点直接决定前端的状态映射。

5. 前端状态管理位置 —— Agent Canvas 里 agent 状态与工具调用展示在哪里？
   要找：Zustand store 的文件、渲染工具调用卡片与确认卡的组件、
   主题切换（深浅色）的实现位置、以及 @openhands/agent-canvas 作为库导出了哪些可复用组件。

【输出格式】
对每个点输出：
- 文件路径（精确到行号）
- 关键类 / 函数名
- 5 行以内的代码摘录
- 「OpsPilot 接入方式」：我们该在哪一行插自己的代码，还是只调它的公开 API

【硬约束】
- 只读，不修改任何文件
- 所有结论必须给出可核对的路径 + 行号，禁止凭文档印象回答
- 如果某个点在代码里找不到或与官方文档不一致，明确标注「与文档不符」并说明实际行为

【产出】
docs/源码索引.md，并在末尾附一节「待核实项清除清单」，
列出需求开发文档里所有 ⚠️ 标记现在是否已被证实。
```

## 提示词 2 · M1 实现 `get_server_health`（第一个运维工具）

```text
【附件】需求开发文档（重点 §A5.2 / §A6.4 / §A6.5 / §A12）+ upstream/software-agent-sdk/。

【前置确认】
提示词 0 的红线 + 提示词 1 产出的《源码索引》已经在场。如果你没有源码索引，
先停下，让我先做提示词 1。

【任务】
实现第一个运维工具 get_server_health，并跑通第一个闭环。

一、工具定义（严格按规格）
- 位置：沿用 SDK 的工具目录约定（参考源码索引第 1 点给出的路径），目录名 get_server_health，
  分 definition.py（Action / Observation / ToolDefinition）与 impl.py（Executor）。
- Action 只有一个字段：server_id（如 hk-ubuntu），类型 str。
  绝对不允许出现 ip / username / password / private_key 字段。
- Observation 字段（严格 JSON schema）：
  server_id, cpu{percent, load_avg, cores, status}, memory{percent, used_gb, total_gb, status},
  disk{used_percent, status}, top_process[{pid, name, cpu}], anomalies[{item, level, hint}]
- annotations：readOnlyHint=True（→ 免确认）
- description 写清楚是"只读获取目标主机健康快照"

二、Executor 实现要点
- 用 Paramiko（或 AsyncSSH）SSH 到目标主机执行只读命令采集。
- 凭据来源：从 credential_ref 解析，解析发生在 Executor 内部，
  解析结果不写入 prompt、不写入 Observation、不写入日志。
- **异常判断写在 Executor 内**：例如 load/cores > 1.5 → cpu.status = "warning"；
  内存 > 90% → memory.status = "warning"。不要让 LLM 自己判断。
- 每个采集命令必须有超时；SSH 连接失败要返回可读的错误信息（区分：认证失败 / 网络不通 / 主机不可达）。

三、必须交付的测试
1. 单元测试：对 Executor 做注入测试（mock SSH 输出），验证 schema 与 anomalies 逻辑。
2. 稳定性测试：同一台机器连续调用两次，输出结构必须完全一致。
3. **泄密测试（最关键）**：打印完整发给模型的 prompt（含工具 schema 与全部历史事件），
   逐字搜索 password / key / 私钥片段 / 明文 IP，必须一个都搜不到。
   把这个测试脚本和搜索输出作为交付物之一。

四、闭环验收（规格 §A12 成功标准 8 条，逐条给证据）
识别服务器 ▸ 调用结构化工具 ▸ SSH 异常返回清晰错误 ▸ 有超时 ▸ 不泄密 ▸
区分正常与异常项 ▸ 所有调用有任务 ID ▸ 可查看执行记录。

【产出】
- 工具代码（definition.py / impl.py / __init__.py）
- 单元测试
- 泄密检查脚本及其输出
- 一段真实对话的完整记录（用户问 → Agent 调用 → 工具返回 → Agent 总结）
```

## 提示词 3 · M2 后端资源与权限底座

```text
【附件】需求开发文档（重点 §A6.5 / §A9 / §A10）。

【任务】实现 OpsPilot 自建后端（FastAPI + SQLite）。这个服务与 OpenHands agent-server 并存，
分工：资源管理 / 任务 / 审批 / 审计 在这个服务；Agent 与工具在 agent-server。

一、数据模型（§A9，6 张表）
ServerConnection / DatabaseConnection / Project / AgentTask / ToolExecution / ApprovalRequest。
注意 ToolExecution 必须包含两个新字段：
- tier：执行时的权限档位，枚举 requested_approval / approve_for_me / full_access
- approval_kind：批准方式，枚举 manual / tier_auto / policy_auto
（tier_auto 表示"由档位自动批准"，与人工批准必须能区分开，这是审计的核心。）

二、API（§A10，全部端点）
/api/connections/servers（含 /test）
/api/connections/databases（含 /test）
/api/chat/sessions
/api/tasks
/api/approvals
另外新增权限档位端点：
GET  /api/session/{session_id}/permission      → 当前档位 + 剩余秒数
POST /api/session/{session_id}/permission      → 变更档位（见下面第 4 点）

三、权限档位状态机（§A6.5，这是本次任务的核心）
- 三档：requested_approval / approve_for_me / full_access
- 默认档按环境：production / staging → requested_approval；development / lab → approve_for_me
- 会话作用域：档位属于 session；切换会话或关闭应用 → 回落默认档
- 自动回落：full_access 默认 30 分钟后自动回落到默认档
- 变更规则（不对称）：
  · 降级（高档→低档）直接生效，不弹任何确认
  · 升级到 approve_for_me 需一次轻量确认
  · 升级到 full_access 必须满足闸门：
    a. 勾选警告（请求体里 must_have_acknowledged=true）
    b. 目标环境为 production 时必须提供环境名且与实际一致
    c. 任一不满足 → 422，返回具体原因
- 每次变更写审计：who / when / from / to / env / sessionId

四、交付要求
1. 迁移脚本可重复执行（幂等）
2. 表结构文档化
3. curl 脚本走通全部端点并保留输出
4. 单元测试覆盖权限状态机的三种回落路径（切会话 / 关应用 / 到时）
5. 单元测试覆盖升级闸门的拒绝路径（未勾选 / 环境名不符）
6. 明确说明：这个服务如何与 agent-server 共存（端口、进程、启动方式），以及
   前端如何同时对接两者

【硬约束】
- 不自建审批引擎 —— 真正的"要不要弹确认"由 agent-server 的 ConfirmationPolicy 决定，
  本服务只存档位、管回落、记审计，并把档位以参数形式传给 agent-server 侧。
- 密码与私钥不入库明文（§A6.4），业务表只存 credential_ref。
```

## 提示词 4 · M3 风险分级与审批

```text
【附件】需求开发文档（重点 §A5.2 / §A6.2 / §A6.5）+ 源码索引。

【任务】把 OpsPilot 的 L0–L5 风险等级接到 OpenHands 的确认机制上，并实现升级闸门与 L5 地板。

一、L0–L5 → ToolAnnotations 映射
框架的 ToolAnnotations 有 4 个位：readOnlyHint / destructiveHint / idempotentHint / openWorldHint。
请产出一张映射表（写入代码常量 + 文档），明确每个 L 级对应的 4 个位的取值。
注意：不要把框架的 SecurityAnalyzer 输出的"低/中/高/未知"四档直接当作我们的 L0–L5，
两者是不同维度，需要显式映射。

二、决策矩阵实现（§A6.5.1，逐格实现并测试）
| 档位           | L0–L1 | L2   | L3   | L4       | L5   |
| 请求审批        | 自动  | 询问 | 询问 | 二次确认  | 拒绝 |
| 帮我批准        | 自动  | 自动 | 自动 | 询问     | 拒绝 |
| 完全访问        | 自动  | 自动 | 自动 | 自动     | 拒绝 |
"自动"= 不弹确认直接执行，但必须写审计，且 approval_kind = tier_auto；
"询问"= 走框架 ConfirmationPolicy 弹确认卡；
"二次确认"= 询问通过后再弹一次高风险确认；
"拒绝"= 不执行并返回明确原因。

三、L5 硬地板
L5 的定义是"没有回滚方案的操作"（删除数据库、清空数据表、重建集群等）。
请实现一个独立的 L5 拦截层，位于所有档位判断之后 —— 也就是说，
即使档位是 full_access，L5 操作仍然被拒绝或强制人工确认。
给出一个测试：full_access 档下执行 DROP DATABASE，必须被拦截。

四、命令危险模式识别（§A5.3）
run_shell 类工具的命令要过一个正则黑名单，命中即抬升风险等级：
- 删除类（rm -rf、dd、mkfs）、防火墙（iptables/ufw/firewalld）、SSH 配置（sshd_config）、
  停服务（systemctl stop/disable）、清历史（history -c）等
- 未命中黑名单的按命令本身语义定级
- 必须可配置、可单测、可扩展（不要把正则写死在 Executor 里）

五、升级闸门后端（§A6.5.3）
- 升级请求必须校验：勾选警告（acknowledged=true）+ 生产环境名匹配
- 校验失败返回 422 和具体原因
- 校验通过 → 写审计 → 生效，并同步更新 agent-server 侧的确认策略
  （这样"完全访问"才真的意味着 L4 不再弹确认）

【产出】
映射表文档 + 决策矩阵实现 + 单元测试（矩阵每一格都要有用例）+
危险模式清单及单测 + 升级闸门测试 + 一段实测记录：
docker ps 不弹卡、docker restart 弹卡、full_access 档下 DROP DATABASE 仍被拦截。
```

## 提示词 6 · 红线审查（合并代码前必跑）

```text
【角色】你是 OpsPilot 的合规审查员。请审查下面这段改动（或这套代码），
逐条核对以下红线，输出"通过 / 违反 + 具体位置 + 修复建议"。

【红线清单】
1. 命名红线：是否出现规格 §A5.2 之外的工具名？是否自造了状态枚举？
   搜索建议：grep -ri "exec_readonly_cmd\|get_system_metrics\|host_id" 。
   （host_id 是被废弃的名字，正确的是 server_id）
2. 状态红线：状态枚举是否与 §A7 的 16 个完全一致，是否出现了小写别名。
3. 风险红线：是否绕过了 L0–L5 的映射？是否有 L5 操作能被自动执行？
4. 权限红线：档位是否只有三档？升级是否走闸门？降级是否被错误地加了确认？
   是否存在"永久生效"的档位（必须按会话）？
5. 凭据红线：打印/搜索完整 prompt、日志、Observation，是否出现密码、私钥、明文 IP？
   Action 字段里是否有 server_id 之外的主机标识？
6. 越权自建：是否自建了审批引擎、凭据服务、Agent 循环、事件总线？
7. 版本红线：依赖是否被浮动升级？agent-client-protocol 是否仍锁在 <0.11？
```
