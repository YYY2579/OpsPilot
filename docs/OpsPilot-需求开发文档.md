# A 部分 · 产品与工程规格

## A1 项目概述

### A1.1 产品定位

OpsPilot 是一个以 AI 聊天为核心的**通用工程 Agent 工作台**。

基于 OpenHands 二次开发，保留其原有的通用工程能力：

- 代码生成与修改、文件读写、Git 操作、终端执行、测试运行、项目分析
- 多步骤任务规划、工具调用、人工审批、任务暂停与恢复

在此基础上，重点增强运维场景能力：

- SSH 服务器管理、数据库连接管理、Docker 管理、Kubernetes 管理
- 日志分析、监控查询、CI/CD 管理、故障排查、变更审批、运维审计

> 核心定位不是"只能做运维的 Agent"，而是：
> **保留通用开发能力，同时让服务器、数据库、容器、集群和监控成为 Agent 的重要工作上下文。**

### A1.2 产品目标

用户可以像使用 ChatGPT、Trae 或 Cline 一样，通过聊天描述任务，由 Agent 自动完成：

1. 理解用户需求 → 2. 识别目标资源 → 3. 制定执行计划 → 4. 调用合适的工具 → 5. 观察工具结果
→ 6. 分析问题 → 7. 生成解决方案 → 8. 在必要时请求用户审批 → 9. 执行变更 → 10. 验证执行结果 → 11. 汇报最终结论

### A1.3 典型使用场景

```text
检查这台服务器最近为什么 CPU 使用率很高
分析 Nginx 502 的原因
检查 Docker 中有哪些异常容器
查看 Kubernetes 中最近重启的 Pod
分析 MySQL 当前连接数和慢查询
修改项目中的 Dockerfile，构建镜像并部署到服务器
检查生产环境的磁盘空间，并给出清理建议
```

### A1.4 产品设计原则

| 原则 | 含义 |
|---|---|
| **聊天优先** | 聊天框是产品主入口。用户不需要先打开终端、选命令、进数据库控制台或开监控页，直接描述问题。 |
| **Agent 能力不受限** | 运维增强不得破坏 OpenHands 原有开发能力。Agent 仍应能读改代码、建文件、跑测试、用 Git、构建镜像、执行部署、处理开发运维混合任务。 |
| **资源上下文优先** | 用户选中的服务器 / 数据库 / 项目 / 集群成为当前聊天上下文，Agent 默认优先针对该上下文执行。 |
| **高风险操作必须可控** | Agent 可提修复方案，但不无条件执行危险操作。高风险操作必须具备：操作说明、目标资源、执行内容、风险等级、预计影响、回滚方案、用户确认、执行记录、执行后验证。 |

### A5.3 `run_shell` 的环境边界（本次修订新增，必读）

`run_shell` 是**通用开发工具**，不是运维工具。它的可用性由**权限档位 + 风险等级**共同决定（见 §A6.5），不按环境硬禁止：

| 环境 | `run_shell` 的默认行为 |
|---|---|
| `lab` / `development` / `staging` | 正常可用，按当前档位与命令风险等级走审批（如 `kill -9`、`history -c` 属 L3，`rm -rf` 属 L4） |
| `production` | **可用，但默认档位为「请求审批」**——每条命令都要人工确认；命令命中黑名单模式（删除、改防火墙、改 SSH、停服务）时至少按 L4 处理（二次确认）。用户可显式升级档位以提升效率，代价是失去逐项确认（见 §A6.5） |

**同时必须做的一件事**：`run_shell` 的命令要过一遍**危险模式识别**（正则黑名单），命中即抬升风险等级——不能因为工具名叫 `run_shell` 就当低风险处理。

> 原版本这里写的是"production 禁止 Agent 自主调用"，属于过度收紧，会显著拖累效率；现改为"高门槛默认值 + 可显式升级"。

## A6 工具调用安全设计

### A6.1 不要让模型直接执行任意命令

**不推荐**

```text
模型生成任意 Shell 命令 → 直接发送到生产服务器执行
```

**推荐流程**

```text
模型选择固定工具 → 工具参数校验 → 权限策略校验
→ 风险等级判断 → 必要时人工审批 → 执行 → 结果验证
```

例如，不直接让模型执行 `rm -rf /var/log/*`，而是提供受控工具 `cleanup_old_logs`：

```json
{
  "server_id": "hk-ubuntu",
  "path": "/var/log",
  "older_than_days": 30,
  "dry_run": true
}
```

### A6.2 工具风险等级（唯一分级表）

```text
L0：纯分析，不执行操作
L1：只读查询
L2：低风险操作
L3：中风险操作，需要确认
L4：高风险操作，需要二次确认
L5：禁止自动执行
```

| 操作 | 风险等级 |
|---|---:|
| 查看磁盘空间 / 查看服务状态 / 查看日志 / 检查端口 | L1 |
| 重载 Nginx | L2 |
| 重启容器 / 修改配置文件 | L3 |
| 重启生产服务 / 删除文件 / 修改防火墙 / 修改 SSH 配置 | L4 |
| 删除数据库 | L5 |

### A6.3 生产环境策略

生产环境的保护**不是一个硬锁，而是一组更严的默认值 + 更重的升级闸门**：

| 项 | 生产环境默认 |
|---|---|
| **权限档位** | **请求审批**（每条写操作都要确认）—— 见 §A6.5 |
| 任意 Shell | 允许，但需逐条确认；命中危险模式按 L4 处理 |
| 删除操作 | 需二次确认（L4） |
| 修改防火墙 / SSH 配置 | 需二次确认（L4） |
| 数据库 | 库连接默认 `readonly=true` |
| 变更 | 必须审批 |
| 审计 | 所有操作必须审计 |

**用户可以把生产环境的档位升级到「帮我批准」或「完全访问」**，但升级需要跨越 §A6.5.3 的闸门（勾选警告 + 输入环境名确认），且升级只对当前会话有效。

> 设计取舍：固定死"生产只读"会把日常巡检、故障排查的效率拖垮。正确做法是**默认从严、升级需付代价**——把判断权交回给用户，但让代价可见。

### A6.4 凭据边界（本次修订写死，必须逐字实现）

这是全项目**不可协商**的安全底线：

1. **模型只持有资源标识**：工具 Action 的入参只允许 `server_id` / `database_id` / `project_id` 等**逻辑标识**。
2. **模型永远拿不到**：SSH 私钥、密码、真实 IP（展示字段除外）、数据库口令、Token、Secret 内容。
3. **凭据解析只发生在工具层（Executor）内部**：由 `credential_ref` 向凭据服务换取连接信息，解析结果**不写入 prompt、不写入 Observation、不写入日志**。
4. **输出脱敏**：任何 Observation 在返回模型前必须过一遍脱敏，命中凭据指纹的字段替换为 `******`。
5. **凭据服务的最低要求**：可审计（每次解析留痕：谁、何时、为哪个 `server_id`）、最小权限（每个 `server_id` 独立凭据）、可轮换（不改业务表即可换钥匙）。
6. **验收方式**：把完整发给模型的 prompt 打印出来，其中搜不到任何密码串、私钥片段或凭据明文。

### A6.5 权限档位模型（本次修订新增，核心）

用户可显式选择 Agent 的自主程度。**档位决定"默认要不要问"，风险等级决定"这一条能不能被档位豁免"。**

#### A6.5.1 三档 × 风险等级决策矩阵

| 档位 | L0–L1 只读 | L2 低风险 | L3 中风险 | L4 高风险 | L5 禁止 |
|---|---|---|---|---|---|
| **请求审批** | 自动 | 询问 | 询问 | 二次确认 | 拒绝 |
| **帮我批准** | 自动 | 自动 | 自动（记审计） | 询问 | 拒绝 |
| **完全访问** | 自动 | 自动 | 自动 | 自动（记审计） | **拒绝** |

**L5 是所有档位的地板。** 任何档位下都不能自动执行；其定义是"**没有回滚方案的操作**"（删除数据库、清空数据表、重建集群等）。这条与 §A3.2「高风险操作必须具备回滚方案」一致——没有回滚方案的操作，本就不该进入自动执行范围。

#### A6.5.2 各档位对用户的含义

| 档位 | 一句话 | 典型场景 |
|---|---|---|
| **请求审批** | 每次写操作都需要你确认 | 生产环境默认；陌生环境；首次操作 |
| **帮我批准** | L2–L3 自动执行，L4 仍会询问 | 开发/测试环境默认；熟悉的日常变更 |
| **完全访问** | L0–L4 自动执行，L5 仍会拦截 | 明确的批量整改、紧急故障处理；仅限可承受风险的窗口 |

#### A6.5.3 升级闸门（不对称）

**升级需要确认，降级不需要。**

| 变更 | 要求 |
|---|---|
| 请求审批 → 帮我批准 | 一次轻量确认 |
| 帮我批准 → 完全访问 / 请求审批 → 完全访问 | 弹出**升级确认面板**，必须满足全部下列条件 |
| 完全访问 → 任意低档 | **一键直接降，不弹窗** |

**升级确认面板必须包含**：

1. **明确列出将失去的保护**，逐条带风险等级（重启服务 L3 / 删除文件 L4 / 修改配置文件 L4 / 修改防火墙与 SSH 配置 L4）
2. **目标环境**高亮显示，生产环境用错误色（红）强调，并显示 `server_id`
3. **列出仍然被拦截的 L5 清单**（让用户知道底线在哪）
4. **勾选框**：「我已了解上述风险，并确认当前环境可承受不逐项确认的执行」——**未勾选时确认按钮必须禁用**
5. **生产环境额外要求输入环境名确认**（防手滑，同 GitHub 删仓库要输仓库名）
6. 按钮顺序：`取消`（默认焦点） / `开启完全访问`（错误色实心）
7. 两行说明：自动回落的时限、以及档位变更与期间操作都会写审计

#### A6.5.4 作用域与时限（必须实现）

| 机制 | 规则 |
|---|---|
| **按会话** | 档位属于当前会话。切换会话 → 回落到该环境的默认档 |
| **关闭应用** | 回落到默认档 |
| **自动回落** | 「完全访问」默认 **30 分钟**后自动回落到该环境的默认档 |
| **默认档** | 生产环境 = 请求审批；staging = 请求审批；development / lab = 帮我批准 |

> 这三条不是可选项。完全访问在生产环境意味着 Agent 可以不等你点头就重启服务——没有时限和会话回落，这个开关在长期使用中必然失控。

#### A6.5.5 审计要求

- 每次**档位变更**记一条：操作人、时间、从哪档到哪档、目标环境、所属会话
- **完全访问期间**的每一次自动执行操作单独记一条，标注"批准方式 = 档位自动批准"而非"人工批准"
- 这两个字段（档位、批准方式）必须出现在 §A9 的 `ToolExecution` 表里

#### A6.5.6 界面呈现契约

1. **档位控件在输入框参数行的最左侧**（该行里最需要被看见的控件），带颜色区分：`请求审批` 绿 / `帮我批准` 蓝 / **`完全访问` 琥珀描边**
2. **开启完全访问后，输入框上方必须有常驻琥珀色横幅**：

   ```text
   ⚠ 完全访问已开启 · 目标 HK-Ubuntu（生产）· 29:41 后自动回落
   ```

   理由：该档位下 Agent 可不等确认即执行生产变更。若只在角落显示小药丸，用户切窗口回来就会忘记自己还开着——那才是真正的事故来源。

3. 输入框下方原来那行静态提示（`当前模式：只读 / 生产环境需要审批后执行变更`）**改为随档位变化的活文字**，并作为档位入口的一部分。

## A7 Agent 工作流（状态机）

建议采用状态机管理任务。

```text
RECEIVED → CLASSIFY_TASK → SELECT_CONTEXT → PLAN → INSPECT → ANALYZE
→ PROPOSE_FIX → WAITING_APPROVAL → EXECUTE → VERIFY → REPORT → COMPLETED
```

异常状态：`FAILED` / `CANCELLED` / `TIMEOUT` / `WAITING_USER`

### A7.1 状态说明 + UI 呈现（本次修订新增：状态机的「UI 如何呈现」列）

**这一列是给前端用的契约**：前端不必为每个状态设计独立页面，按本表渲染即可。

| 状态 | 含义 | 进入条件 | **UI 如何呈现** |
|---|---|---|---|
| `RECEIVED` | 接收用户消息 | 用户发出消息 | 用户气泡入列；输入框转为禁用并显示"Agent 处理中" |
| `CLASSIFY_TASK` | 判断任务类型（开发/运维/数据库/Docker/K8s/监控/混合） | 消息已入列 | **不单独呈现**，合并进"规划执行路径"的一行文本 |
| `SELECT_CONTEXT` | 确定目标服务器/数据库/项目/集群 | 任务类型已定 | 顶部上下文条高亮目标资源；多目标时显示多目标标签。**不弹卡片** |
| `PLAN` | 生成执行计划 | 上下文已定 | 聊天区插入**可折叠的计划卡**（步骤链），每步有状态点 |
| `INSPECT` | 调用只读工具获取事实 | 计划已生成 | 步骤链中对应节点转"进行中"；插入**工具调用卡**（spinner） |
| `ANALYZE` | 根据工具结果判断原因 | 只读工具返回 | 工具卡转"已完成"。**不单独呈现**，结论并入下一段 Markdown |
| `PROPOSE_FIX` | 生成修复方案、风险与回滚计划 | 已完成分析 | 输出 Markdown：标题 + 列表 + 表格 + 风险提示 + 修复建议 |
| `WAITING_APPROVAL` | 等待用户批准高风险操作 | 命中 confirmation policy | **弹出人工确认卡**（醒目）：操作/目标/风险等级/执行内容/预计影响/回滚方案 + 四个按钮。输入框禁用，提示"等待你批准后继续" |
| `EXECUTE` | 执行已批准的操作 | 用户批准 | 确认卡收起为"已批准"；步骤链插入执行节点 + 终端输出块。**执行中不显示取消以外的操作** |
| `VERIFY` | 校验服务/进程/端口/日志/业务接口是否恢复 | 执行完成 | 步骤链插入"验证"节点，结果用绿色/红色徽标标注 |
| `REPORT` | 输出最终汇报 | 验证完成 | **任务总结卡**：问题 / 处理 / 结果 / 验证 / 后续建议 |
| `COMPLETED` | 任务完成 | 汇报完成 | 顶部任务状态点转"已完成"；输入框恢复可用 |
| `FAILED` | 任务失败 | 任一环节不可恢复错误 | 红色错误卡，含失败原因 + 重试按钮。**必须给出明确原因** |
| `CANCELLED` | 用户取消 | 用户主动取消 | 计划卡整体置灰，标注"已取消" |
| `TIMEOUT` | 工具或任务超时 | 超过工具超时阈值 | **轻量 toast + 步骤链节点标红**，不占用独立页面 |
| `WAITING_USER` | 等待用户补充信息 | Agent 需要澄清 | 输入框恢复可用 + 聊天区插入提问气泡（普通消息样式，非确认卡） |

> 设计要点：`CLASSIFY_TASK` / `ANALYZE` 这类**内部决策状态不单独占版面**；只有 `WAITING_APPROVAL` 和 `REPORT` 需要高视觉权重的卡片。这样 12 个状态只对应 **4 种 UI 载体**（步骤链、工具卡、确认卡、总结卡），前端工作量可控。

## A14 验收标准

**Agent**：能通过聊天完成任务；能调用多个工具；能根据工具结果继续执行；能处理工具失败；能请求人工审批；能完成执行后验证；不因增加运维功能而失去开发能力。

**SSH**：支持密钥认证、连接测试、超时、错误提示、服务器分组、环境标签、凭据安全存储。

**安全**：生产环境默认只读；危险操作必须审批；工具参数必须校验；不允许模型直接访问凭据；不允许日志输出密码和私钥；所有变更有审计记录；关键操作支持回滚或恢复。

**UI**：聊天区是视觉核心；左侧资源选择不会打断聊天；右侧展示实时辅助信息；工具调用过程清晰；审批状态明显；任务失败有明确原因；支持深色和浅色主题；适合桌面端使用。

## A15 最终产品定义

> 我打开的是一个 AI 工程助手。我可以像和 ChatGPT 聊天一样描述问题，但它能够连接服务器、数据库、项目、容器、Kubernetes 和监控系统，自动调用工具完成任务。

```text
聊天区：主入口
Agent：任务执行核心
左侧：资源和上下文
右侧：状态和工具辅助
工具层：连接真实环境
审批层：控制高风险操作
审计层：记录所有变更
```

**不要把产品做成传统 SSH 客户端、数据库客户端或监控大屏。** 它们只是 Agent 的资源入口和工具能力。

```text
通用工程 Agent + 运维资源管理 + 运维工具体系 + 安全审批 + 可视化任务工作台
```

**工具调用卡**（支持展开）

基础态显示：工具名称、目标、状态、耗时。展开后显示：工具名称、参数、目标资源、执行命令、标准输出、错误输出、执行耗时、风险等级。

工具卡状态：`等待执行` / `执行中` / `已完成` / `执行失败` / `等待批准`

**Agent 最终分析**：清晰 Markdown，支持标题、列表、代码块、表格、风险提示、修复建议、任务总结。

## B5 聊天输入框

底部大尺寸输入框，占中间区域宽度。**内部为三行结构**：

```text
┌──────────────────────────────────────────────────────────────┐
│ 占位符：描述你想完成的任务，例如：检查 Nginx 502 的原因        │  ← 输入区
├──────────────────────────────────────────────────────────────┤
│ [＋添加文件] [服务器] [数据库] [添加上下文] [使用终端]         │  ← 快捷操作行
├──────────────────────────────────────────────────────────────┤
│  [DeepSeek-V3 ▾]  [思考 中 ▾]  [Auto|Plan|Execute|Review]  [↑] │  ← 参数行
└──────────────────────────────────────────────────────────────┘
当前模式：只读      生产环境需要审批后执行变更
```

**参数行（新增，紧贴发送按钮）**

从左到右依次为：**权限档位** → 模型 → 思考等级 → Agent 模式 → 发送按钮。

| 控件 | 形态 | 取值 |
|---|---|---|
| **权限档位** | 药丸形下拉，**在该行最左侧** | `请求审批`（绿）/ `帮我批准`（蓝）/ `完全访问`（琥珀描边），详见 §A6.5 |
| 模型选择 | 药丸形下拉 | 当前模型名，如 `DeepSeek-V3` |
| 思考等级 | 药丸形下拉 | `低` / `中` / `高`（默认 中） |
| Agent 模式 | 四段分段控件 | `Auto` / `Plan` / `Execute` / `Review`，选中项 accent 底白字 |
| 发送 | 30×30 圆角方块 | 禁用态转灰 |

**上下文环 `<ContextRing>`（§B5.1，发送按钮左侧）**

- 位置：参数行最右、发送按钮左侧；30×30 圆环，环心显示占用百分比。
- 颜色阈值：**<70% 绿（--ok）｜70–90% 琥珀（--warn）｜>90% 红（--err）**；>90% 时输入框上方追加与完全访问横幅同规格的提示条「上下文将满，建议压缩或新开会话」。
- hover / 点击弹出明细面板：已用/上限 tokens、输入与输出分项、**缓存命中率**（命中 / 未命中）、上次压缩发生与否、按最近 5 轮增量估算的"还可容纳轮数"。
- 明细里必须包含一行解释：**压缩发生时前缀变化 → 缓存命中率骤降（本轮成本上升）**。
- 数据来源：`ConversationState.stats` + LLM usage（各家字段不同：DeepSeek 是 `prompt_cache_hit_tokens / prompt_cache_miss_tokens`，Anthropic 是 `cache_read_input_tokens / cache_creation_input_tokens`，后端必须归一化）；压缩事件用 SDK 的 `Condensation`（源码索引 §2.1.7）并在聊天时间线打标记。
- 后端新增接口：`GET /api/tasks/{id}/context-usage`（M2 骨架，M6 接真数据）。

**权限档位的两个必要配套**（详见 §A6.5.6）：

- **完全访问时**，输入框上方常驻琥珀色横幅：`⚠ 完全访问已开启 · 目标 HK-Ubuntu（生产）· 29:41 后自动回落`
- 输入框下方的静态提示改为**随档位变化的活文字**：请求审批 → 「每次写操作都需要你确认」；帮我批准 → 「L2–L3 自动执行，L4 仍会询问」；完全访问 → 「L0–L4 自动执行，L5 仍会拦截」

> **为什么下移**：模型和模式是"每次发消息前会调整"的参数，贴在发送按钮旁边符合操作路径，也让顶部栏保持干净。参考 Codex 的输入框布局。

**快捷操作行**：添加文件 / 选择服务器 / 选择数据库 / 添加上下文 / 使用终端（原「运行任务」由发送按钮承担，不再单列）。

**权限提示**：输入框下方常驻，右对齐 ——

```text
当前模式：只读
生产环境需要审批后执行变更
```

**禁用态**：`WAITING_APPROVAL` 时输入框整体 55% 透明度，占位符改为「等待你批准后继续…」，发送按钮转灰。

## B6 右侧辅助面板（320px，可折叠）

右侧**不是第二个聊天框**，而是辅助信息面板。顶部标签页：`概览` / `工具` / `任务` / `日志`

**概览**：主机名、操作系统、CPU、内存、磁盘、Load Average、服务状态、网络状态

**工具**：当前 Agent 调用过的工具列表，每个显示状态、耗时、目标、是否有风险。点击工具后聊天区定位到对应工具调用记录。

**任务**：当前任务、已完成步骤、进行中步骤、待执行步骤；底部显示任务时间线。

**日志**：当前资源最近日志摘要，支持搜索、时间范围、日志级别筛选、复制日志、在聊天中分析日志。

## B7 关键交互

**1. 服务器切换**：点击左侧服务器后 → 中间顶部上下文更新 → 右侧概览更新 → 聊天输入框提示当前服务器 → 后续 Agent 工具默认作用于当前服务器 → 任务涉及多服务器时显示多目标标签。

**2. 数据库切换**：点击数据库连接后 → 左侧展开数据库树 → 右侧显示连接信息 → 聊天上下文显示当前数据库 → 支持选择数据库和数据表 → 聊天中可直接请求 SQL 分析。

**3. 高风险操作审批**：当 Agent 需要重启服务、修改配置、删除文件或修改数据库时，在聊天区显示醒目的审批卡片：

```text
需要你的批准
操作：重启 backend 容器
目标：HK-Ubuntu
风险：中（L3）
预计影响：服务中断 5～15 秒
回滚方案：重新启动原容器
```

按钮：`查看命令` / `批准执行` / `拒绝` / `修改方案`

> **不要让危险操作只显示一个普通的"执行"按钮。**

**4. 任务完成**：显示总结卡片——任务已完成 / 问题 / 处理 / 结果 / 验证

**5. 多任务和历史**：左侧任务历史显示历史任务（检查 Nginx 502 / 分析 MySQL 慢查询 / 检查磁盘空间 / 部署个人博客 / 查看 K8s Pod 异常）。点击后恢复完整聊天和工具调用记录。

## B11 最终设计目标

> "我打开的是一个 AI 工程助手，我可以像和 ChatGPT 聊天一样描述问题，但它能连接我的服务器、数据库、项目和监控系统，并且真正调用工具完成任务。"

## B12 主题切换与响应式（本次新增）

### B12.1 深色 / 浅色切换按钮

- **位置**：顶部栏右侧，模式分段控件（Auto/Plan/Execute/Review）与设置按钮之间。
- **形态**：28×28 图标按钮，与设置按钮同规格（7px 圆角、`--text2` 色）。
- **图标语义（跟随"点击后会变成什么"）**：
  - 当前深色 → 显示 **太阳图标**（点击切到浅色）
  - 当前浅色 → 显示 **月亮图标**（点击切到深色）
- **默认**：深色（`--bg: #111318`）。首次启动不读取系统偏好，固定深色。
- **切换范围**：整个应用，通过切换根节点的 `light` 类实现；**不允许**组件各自实现主题。
- **持久化**：记录用户选择，下次启动恢复。
- **约束**：按钮本身不改变任何布局尺寸，切换前后布局必须完全一致（只换色值）。

### B12.2 响应式规则（不同窗口比例下自动伸缩，保证布局完整）

**总原则：任何窗口尺寸下都不允许出现横向滚动条，也不允许内容被裁切；面板让位优先级为「右栏 → 左栏」。**

| 窗口宽度 | 左栏 | 中栏 | 右栏 |
|---|---|---|---|
| ≥ 1700px | 260px | 弹性，内容列限宽 **1120px** 并居中 | 320px |
| 1440 ~ 1699px | 260px | 弹性，内容列限宽 **1040px** 并居中 | 320px |
| 1280 ~ 1439px | 236px | 弹性 | 288px |
| 1024 ~ 1279px | 220px | 弹性 | **自动收起为 44px 图标条** |
| 960 ~ 1023px | 200px | 弹性 | 44px 图标条 |
| < 960px | **自动收起为 48px 图标条** | 弹性 | 44px 图标条 |

**窗口高度自适应**

| 窗口高度 | 变化 |
|---|---|
| < 840px | 聊天流内边距与间距收紧 |
| < 720px | 顶栏降到 50px、上下文条降到 36px，聊天流/右栏内边距进一步收紧，欢迎页标题降到 20px |

**必须满足的三条硬要求**

1. **纵向：聊天流内滚动，输入框永远贴在底部可见。** 内容再长也不裁切、不把输入框顶出屏幕。
2. **横向：只让面板让位，不让内容变形。** 面板收起后，其位置由 44/48px 图标条承接（保留概览/工具/任务/日志与资源分类入口），不是直接消失。
3. **超宽屏：聊天列限宽居中。** 避免在 21:9 等超宽屏上出现"一行文字横跨 1900px"的阅读灾难；限宽值见上表。

> 窄窗口下右侧面板的**自动**收起，与用户**手动**点击收起是同一个视觉形态（44px 图标条），但触发源不同；用户手动收起后，即使窗口变宽也应保持收起，直到用户手动展开。

# C 部分 · 与 OpenHands V1 的对接基线

> 本部分用于区分**框架已提供**和**OpsPilot 需要自建**，避免重复造轮子。上游已拉取到 `upstream/`，版本基线见项目根 `README.md`。

| OpsPilot 需要的能力 | OpenHands V1 是否已提供 | 结论 |
|---|---|---|
| Agent Loop / 多步规划 / 工具调用 | ✅ 已提供（SDK） | 直接复用，不要自己写 |
| 工具定义方式 | ✅ Action / Observation / ToolExecutor / ToolDefinition | 每个运维能力 = 一个 ToolDefinition |
| 工具注册与发现 | ✅ ToolRegistry | 直接复用 |
| MCP 扩展 | ✅ 原生支持（stdio / SSE / Streamable HTTP / OAuth） | 运维工具可做成 MCP Server，不必改核心 |
| 危险分级的行为提示位 | ✅ `ToolAnnotations`（readOnly / destructive / idempotent / openWorld） | L0–L5 需映射到这 4 个位 |
| 风险评级 + 确认策略 | ✅ SecurityAnalyzer + ConfirmationPolicy | **不要自建审批引擎**，只做 L 级映射 |
| 凭据隔离与脱敏 | ✅ SecretRegistry（会话级隔离、输出自动脱敏、可轮换） | **不要自建凭据服务**，在其上加 `credential_ref` 解析 |
| 事件流与实时推送 | ✅ REST + WebSocket | 直接复用 |
| 会话持久化 / 暂停恢复 / 分叉 | ✅ ConversationState + append-only EventLog | 直接复用 |
| 上下文压缩 | ✅ Condenser | 直接复用 |
| 执行隔离 | ✅ LocalWorkspace / DockerWorkspace / RemoteAPIWorkspace | 按环境选择 |
| 多模型路由 | ✅ LiteLLM，100+ 提供商 | 直接复用 |
| 前端工作台 | ⚠️ Agent Canvas（React 19 + TS + Vite + Tailwind + Zustand）可作为**库**嵌入 | **三栏布局需自己改**，组件可复用 |
| 资源管理（服务器/数据库/项目） | ❌ 不提供 | **自建**（FastAPI 服务） |
| 任务状态投影（12 态） | ⚠️ 事件驱动，不是显式状态机 | **自建**一层投影 |
| 审计记录 | ⚠️ 有事件日志，但没有业务级审计表 | **自建**（`ToolExecution` / `ApprovalRequest`） |
| 多租户 / SSO / RBAC | ❌ 开源版没有 | MVP 不做 |
