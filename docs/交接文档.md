## 一、这个项目是什么

**一句话**：OpsPilot 是一个以 AI 聊天为核心的**通用工程 Agent 工作台**，基于 [OpenHands](https://github.com/OpenHands/OpenHands)（MIT 许可）二次开发——在保留它原有的代码生成、文件操作、终端执行、Git、测试运行等**通用工程能力**之上，叠加 SSH、数据库、Docker、Kubernetes、日志与监控的**运维能力**。

**它是什么、不是什么**（这个区分决定了所有设计）：

| 它是 | 它不是 |
|---|---|
| 一个能连服务器、数据库、容器、集群的 AI 工程助手 | ❌ 传统的 SSH 客户端 |
| 用户用自然语言描述任务，Agent 自动规划并调用工具 | ❌ 数据库客户端 |
| 保留全部通用开发能力，运维只是增强 | ❌ 监控大屏 |
| 桌面端三栏工作台（左资源树 / 中聊天 / 右辅助面板） | ❌ "只能做运维的受限 Agent" |
|  | ❌ 多租户 SaaS（MVP 不做） |

**核心体验**（规格 §A15）：用户像跟 ChatGPT 聊天一样说「检查这台服务器为什么 CPU 高」，Agent 自己识别目标服务器 → 调用只读工具 → 分析结果 → 给出结论 → 需要改动时弹出审批卡等人确认 → 批准后执行 → 验证 → 汇报。

## 五、十条铁律（红线，违反任何一条都要回滚）

1. **命名不得改。** 工具名只能来自 §A5.2 的命名表；任务状态只能是 §A7 的 16 个枚举值（`RECEIVED` / `CLASSIFY_TASK` / … / `COMPLETED` / `FAILED` / `CANCELLED` / `TIMEOUT` / `WAITING_USER`）；风险等级只有 L0–L5。**禁止**在代码里另起小写别名或自造工具名。
2. **效果图是示意，不是规格。** 里面的主机名、IP、百分比、耗时、日志全是**演示占位**。与规格冲突时以规格为准。
3. **原型 HTML 不是规格。** 它是像素参考和 DOM 结构参考。
4. **凭据边界不可协商**（§A6.4）：工具 Action 只带 `server_id` 等逻辑标识；私钥 / 密码 / 真实 IP 永不进入 prompt、Observation、日志；解析只在工具层（Executor）内部完成；输出必须脱敏。**验收方式是打印完整 prompt 逐字搜索。**
5. **L5 是所有档位的地板。** 任何权限档位（包括完全访问）下，L5 类不可逆操作（删除数据库、清空数据表、重建集群）都不得自动执行。
6. **不做 ops / dev 领域双模式。** Agent 只有一个，工具表是统一的。Agent 是否能自主执行由**环境 + 风险等级 + 资源上下文**决定，不由"模式"决定。
7. **不要自建框架已有的东西**：审批引擎（用 `ConfirmationPolicy` + `SecurityAnalyzer`）、凭据隔离（用 `SecretRegistry`）、Agent 循环（用 SDK）、事件流（用 REST + WebSocket）。自建 = 白干一遍且更容易出错。
8. **上游版本 pin 死**：agent-server `1.46.0` / agent-canvas `1.18.0` / automation `1.11.1`。升级是单独的任务，**绝不**顺手 `npm update` / `pip install -U`。
9. **异常判断写在工具 Executor 内**，不交给 LLM —— 输出才稳定、可测、换模型不掉链子。
10. **里程碑以"能演示"为验收标准**，不以"写完了"为标准。每个任务的验收都需要**可复现证据**（截图 / curl 输出 / 单测 / 打印的 prompt）。

## 六、技术底座：OpenHands 现状

### 6.1 结构

OpenHands V1 不是单体仓库，而是一套 SDK + 多个可组合服务 + 一个可嵌入的前端包：

```text
Agent Canvas（React 19 + Vite + Tailwind + Zustand，npm: @openhands/agent-canvas）
        │  REST + WebSocket
Agent Server（Python，默认 :18000）── 跑 Agent 与工具
Automation Backend（:18001）──────── 定时 / 事件触发工作流
```

SDK 四个 Python 包：`openhands-sdk`（核心抽象）/ `openhands-tools`（工具实现）/ `openhands-workspace`（执行环境）/ `openhands-agent-server`（REST+WebSocket 服务）。

### 6.2 框架已提供 → **不要自建**

| 能力 | 框架提供物 | OpsPilot 要做的 |
|---|---|---|
| Agent 循环 / 多步规划 / 工具调用 | SDK Agent + Conversation | 直接用 |
| 工具定义与注册 | `Action` / `Observation` / `ToolExecutor` / `ToolDefinition` + `ToolRegistry` | 每个运维能力写一个 ToolDefinition |
| 扩展方式 | **MCP 原生支持** | 可选：后期把工具包暴露为 MCP Server |
| 危险分级的底层位 | `ToolAnnotations`（readOnly / destructive / idempotent / openWorld） | 把 L0–L5 映射到这 4 个位 |
| **风险评级 + 确认策略** | `SecurityAnalyzer` + `ConfirmationPolicy` | 只做 L 级映射，**不自建审批引擎** |
| **凭据隔离与脱敏** | `SecretRegistry`（会话级隔离、输出自动脱敏、可轮换） | 只接 `credential_ref` 解析 |
| 事件流 / 暂停恢复 / 持久化 | REST + WebSocket + append-only EventLog + Condenser | 直接用 |
| 执行隔离 | `LocalWorkspace` / `DockerWorkspace` / `RemoteAPIWorkspace` | 按环境选 |
| 多模型 | LiteLLM，100+ 提供商 | 直接用 |
| 行为约束 | `Skills` / `Hooks`（可阻断危险命令）/ `Plugin` | 用 Hooks 兜底危险命令 |

### 6.3 需要自建（OpsPilot 的真正工作量）

1. **资源管理后端**（FastAPI + SQLite）：服务器 / 数据库 / 项目 的 CRUD、连接测试、`credential_ref` 管理、任务与审批与审计的表
2. **任务状态投影**：OpenHands 是事件驱动的，没有显式状态机；要把 Event 流投影成 §A7 的 16 态
3. **前端三栏工作台**：Agent Canvas 的 Sidebar 是会话列表，不是资源树；布局必须自己写（组件可复用）
4. **业务级审计表**：`ToolExecution`（含 `tier` / `approval_kind` 字段）、`ApprovalRequest`

### 8.2 已知坑（上游自己标注的）

**必须把 `agent-client-protocol` 锁在 `<0.11`。**

## 九、四项已定技术决策（初衷与理想态）

> 这四项**已经定死，不再是待办**。写在这里的目的是让接手的人知道**为什么这么定**——如果你认为某一条的前提已经变了（比如需要把 OpenHands 原版 Canvas 一起打包），在 M5 开工前提出，同步更新规格与效果图；开工后再推翻，成本会高很多。

### 决策 1 · 桌面封装 = **Tauri**

- **初衷**：OpsPilot 是要**长期开着**的工程工具，不是偶尔打开的应用。而它的全部业务逻辑都在 Python 侧（自建 FastAPI + OpenHands agent-server），桌面壳只负责加载前端——这正是 Tauri 的甜区，同时完全绕开了"壳里要写 Rust"这个短板。Electron 最大的优势（Node 主进程）在这里根本用不上。
- **理想态**：三端安装包都在 30MB 以内，常驻内存与一个浏览器标签页相当；**前端代码与壳完全解耦**——将来就算换壳（Wails、原生 WebView），业务代码一行不改。
- **代价（已接受）**：构建机要装 Rust 工具链（一次性）；Windows 依赖 WebView2（Win10 1803+ 与 Win11 自带）。

### 决策 2 · 菜单栏 = **自绘**

- **初衷**：OpsPilot 的界面是深度定制的产品，不是通用窗口。自绘保证 ① 三平台视觉完全一致 ② 与效果图像素对齐 ③ 菜单项可以承载**业务语义**（如「导出当前报告」「检查更新」），而不只是系统能力。原生菜单的外观跟随系统，无法做到这三点。
- **理想态**：自绘菜单栏负责**视觉与业务动作**，系统级快捷键注册负责**全局可达**（比如在其他应用里也能呼出快速命令）——视觉归我们，快捷键归系统，两者不打架。
- **代价（已接受）**：窗口拖拽、最大化、系统菜单行为需要自己处理；原生菜单带来的"系统级熟悉感"会打折扣。

### 决策 3 · 底部面板 / 打开终端 = **MVP 置灰，v2 再做**

- **初衷**：规格 §A3.1 说「聊天框是产品的主入口」，§B11 说「中间聊天区永远是核心」，原始需求里明确警告过"不要把界面做成复杂的后台系统"。底部面板是**第三块辅助区**，加上去会让屏幕变成三栏 + 底栏的四分格式，稀释聊天主线。
- 而且**MVP 阶段并不缺终端可视性**：每条命令的执行命令、标准输出、错误输出都在聊天区的工具卡里可见，可展开。
- **理想态**：v2 引入可折叠的底部面板，承载**实时终端**与**原始日志流**——它是聊天里工具卡的"全屏展开版"，默认收起，由菜单 / `Ctrl+`` ` `` 唤起，且必须与聊天区**联动**（点工具卡 → 底部面板定位到对应输出）。
- **MVP 处理**：菜单「视图」里的「切换底部面板」「打开终端」**置灰**，hover 提示「v2 提供」；其余菜单项正常可用。

### 决策 4 · 上游 patch 策略 = **提 PR 优先，禁止静默 fork**

- **初衷**：我们选择"组装式"而不是 fork，就是为了跟着上游走（上游日活跃，Beta 组件还在快速演进）。一旦在本地维护私有 patch 且不回流，就等于变相 fork——M0-2 pin 版本的意义就没了，上游每次升级你都要重新合并一遍私有补丁。
- **理想态**：对上游的任何改动都以 **PR 形式回流**（OpenHands 是 MIT，欢迎贡献）；PR 合并前，本地用 patch 文件过渡，**每个 patch 必须有 issue 跟踪 + 在 README 登记**，并且升上游版本时第一个检查项就是"这些 patch 还需不需要"。
- **硬规则**：`upstream/` 目录**不允许直接改代码**。它只用于阅读、调试、复现问题。

> 影响范围：M5-1 的脚手架按 Tauri 起；M5-3 的菜单栏按自绘实现；M0-5 由"拍板"改为"落档确认"。

## 十、FAQ（为什么这么设计）

**Q1：为什么基于 OpenHands，而不是从零写？**
因为最难自研的四件事它已经做好了：Agent 循环、审批引擎、凭据隔离、事件流。自己写这四样至少多花几个月，而且大概率不如它稳定（它在 SWE-Bench Verified 上用 Claude Sonnet 4.5 跑到 72%）。OpsPilot 的差异化在**工具层 + 资源管理 + 三栏 UI**，这三样本来就要自己写。

**Q2：为什么不做 ops / dev 双模式？**
因为技术上没有意义——OpenHands 的 Agent 是无状态纯函数，运维工具是**注册进**统一工具表的，不是替换开发工具。做成双模式等于把通用能力锁进一个模式，混合任务（改 Dockerfile → 构建 → SSH 部署 → 验证）要来回切。而且"能不能自主执行"由**环境 + 风险等级 + 资源上下文**决定，比"属于哪个领域"准确得多。

**Q3：为什么生产环境不是硬性只读？**
因为硬锁会把日常巡检和故障排查的效率拖垮。现在的设计是**默认从严 + 升级需付代价**：生产默认档是「请求审批」（每条写操作都要确认），用户可以升级到「帮我批准」或「完全访问」，但必须跨越升级闸门（勾选警告 + 生产环境要输环境名），且升级只对当前会话有效、30 分钟自动回落、全程审计。**唯一不变的地板是 L5**：没有回滚方案的操作在任何档位下都不能自动执行。

**Q4：为什么要自建 FastAPI，而不是直接 fork OpenHands？**
因为 OpsPilot 的差异化（运维工具、凭据边界、资源管理、三栏 UI）**没有一样需要改 OpenHands 的核心**。fork 一个还在快速演进的上游（Beta 组件、日活跃）来做垂直产品，换来的是长期维护负担。组装式让耦合面最小。

**Q5：效果图和规格冲突时听谁的？**
**永远听规格。** 效果图里的数字全是演示占位。规格 §B9 列出了每张效果图对应的状态。

**Q6：凭据到底存哪？**
密码和私钥**绝不**存业务表。走系统密钥环 / 加密存储 / Secret 服务，业务表里只存 `credential_ref`（一个引用）。模型只看到 `server_id`，解析发生在工具层内部。框架的 `SecretRegistry` 已经做了会话级隔离和输出自动脱敏。

**Q7：为什么状态机有 16 个状态，前端却只有 4 种卡片？**
因为其中一半是内部决策状态（`CLASSIFY_TASK`、`ANALYZE`），屏幕上什么都不显示；`TIMEOUT` 只用 toast。详见规格 §A7.1 的「UI 如何呈现」列——**这一列是给前端的契约，照着做就不会做 16 个页面**。
